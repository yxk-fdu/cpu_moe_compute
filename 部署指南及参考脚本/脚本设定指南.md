# 脚本设定指南

使用 [参考启动脚本.sh](参考启动脚本.sh)。本脚本使用共享 NZ 权重，默认单卡 BS1、DSpark7、CPU 计算开启、下一层预取关闭。

## 1. 准备配套版本

用同一组配套源码构建 vLLM-Ascend 和 kt-kernel。参考环境使用 vLLM 0.30.0。模型目录应包含支持的 MXFP4 checkpoint，加载时由 vLLM-Ascend 生成共享 NZ 权重和 scale。

在已有配套容器中安装Ascend源码，不升级vLLM/Torch。先设置 `ASCEND_REPO`（固定提交源码目录）、`BUILD_ROOT`（本次新的构建输出目录），并加载CANN环境：

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
export ASCEND_REPO=/workspace/vllm-ascend
export BUILD_ROOT=/workspace/cpu-moe-build
# 153为Ascend950PR；其他硬件按实际SoC设置并重新验证。
export SOC_VERSION=ascend950pr_9599
cd "$ASCEND_REPO"
git submodule update --init --recursive
MAX_JOBS=2 python -m pip install -e . --no-build-isolation --no-deps
python -m pip install -e ./csrc/lrc_policy --no-build-isolation --no-deps
(cd csrc/lrc_policy && python setup_npu_wait.py build_ext --inplace)
# 构建 CPU MoE 的映射结果合并辅助库。
bash csrc/cpu_moe_mapped_combine/build.sh "$BUILD_ROOT/mapped-combine" "$SOC_VERSION"
```

在同一容器中编译 CPU 后端，构建目录必须尚不存在。

```bash
bash cpu_moe/dependencies/ktransformers-AK/kt-kernel/build_ascend_cpu_moe.sh /workspace/kt-nz-build
export KT_BUILD=/workspace/kt-nz-build/package
```

`KT_BUILD` 指向包含 `kt_kernel/` 的 Python 包目录。构建脚本会检查 `NZMOE`、原生派发 ABI 和线程池拓扑预检接口。

## 普通CPU计算

[普通CPU计算.sh](../cpu_moe/普通CPU计算.sh) 默认单卡 BS1，关闭 DSpark 和下一层专家预取。需要切换这两个选项时可以使用 [参考启动脚本.sh](参考启动脚本.sh)。

## 2. 填写路径并启动

在容器内填写已准备好的源码、构建输出和模型路径。

```bash
export WORKSPACE=/workspace
export ASCEND_REPO="$WORKSPACE/vllm-ascend"
export KT_BUILD=/workspace/kt-nz-build/package
export MODEL_PATH=/models/DeepSeek-V4-Flash-0731
export LOG_ROOT=/workspace/logs/cpu_moe

# 从本指南所在目录执行；此步只检查依赖和配置，不加载模型。
CPU_MOE_CHECK_ONLY=1 bash 参考启动脚本.sh

# 每次只启动一种配置，切换前停止上一服务。
BS=1 DSPARK=7 PREFETCH=0 bash 参考启动脚本.sh
# 其他选择：DSPARK=0关闭DSpark；PREFETCH=1开启下一层预取。
```

`WORKSPACE` 提供默认工作目录；`ASCEND_REPO` 与 `KT_BUILD` 可单独指定。`MODEL_PATH` 是原始 MXFP4 模型目录。`LOG_ROOT` 用于本次运行的日志、配置快照和profile输出，每次创建独立子目录。

脚本前台运行，Ctrl+C正常退出。切换配置时确认API与EngineCore都已退出。入口将指定的 `ASCEND_REPO` 加入Python搜索路径并核对实际导入位置，避免误用另一份已安装Ascend源码；缺少原生扩展或mapped-combine辅助库时会在模型加载前报出。启动后查看 `server.log`、`additional_config.json`、`launch-config.json`，核对实际配置。

## 3. 需要按机器调整的参数

环境变量可写在启动命令前。先按目标机器核对拓扑和容器允许的 CPU。

| 环境变量 | 脚本默认值 | 设置说明 |
| --- | --- | --- |
| `NPU` / `PORT` | `4` / `8144` | 使用空闲物理卡和空闲端口；物理卡4在进程内映射为逻辑卡0。 |
| `BS` | `1` | `max_num_seqs`；性能测试的请求并发必须与它一致。 |
| `DSPARK` | `0`或`7`，默认7 | 0不传推测配置；7表示DSpark草拟7个token，一个step最多8个token。 |
| `PREFETCH` | `0`或`1`，默认0 | 开关下一层预取；开启后上限固定为1个专家。 |
| `NUMA_NODE` / `CPU_THREADS` | 自动 | 可手动指定计算 NUMA 和线程数。默认以 worker 的 CPU affinity 选可用物理核，先为 poll、completion、DMA 留核。 |
| `KT_MOE_POLL_CPU` / `KT_MOE_COMPLETION_CPU` / `DMA_CPU` | 自动分配 | 可选的逻辑 CPU，三者和计算池需要使用不同物理核。 |
| `HOST_WEIGHT_NUMA_NODE` | 跟随实际计算节点 | 共享 NZ 权重所在的 NUMA 节点。 |
| `CPU_MOE_PROFILE` | 默认1 | 设置CPU事件输出路径，详细原生事件由profiler采集窗口开关控制；0不输出这份CPU trace。 |

启动前用 `npu-smi info`、`lscpu -e=CPU,NODE,CORE,SOCKET`、`numactl --hardware` 核对卡、核、容器允许集合及节点空闲内存。计算核、监测核与DMA核要在允许集合内，且没有明显争用。

启动日志记录计算节点、线程 CPU、三个服务核和权重 NUMA。内存首选节点允许回退，启动后可用 `numastat -p <EngineCore PID>` 和 `/proc/<PID>/task/<TID>/status` 检查实际内存与线程落点。不能仅凭节点配置值认定绑定已生效。

## 4. 保留在脚本里的关键配置

CPU 和专家搬运成本在共享 NZ 权重加载后自动校准，启动日志会记录测量结果。

| 配置 | 本次取值及含义 |
| --- | --- |
| `cpu_moe.enabled` | 给所有符合条件的 MoE 层挂上 CPU 后端。图回放中的计算和 DMA 由原生派发器提交。 |
| `enable_cpu_binding` | **false**，避免上层绑核覆盖kt后端安排。CPU后端本身仍绑核。 |
| CPU MoE 调度 | 固定使用 `load_balance`，按实际expert-token工作量和传输成本分配；LRC选择淘汰对象，优先搬被选择次数多的专家。 |
| CPU成本 | 分别测同一专家处理 1 和 2 个 token，区分首次计算和额外路由的成本。 |
| 搬运与NPU成本 | 测一个专家全部物理字段的 H2D 时间。`balance_npu_fixed_us=200` 仍按层估算 NPU 计算。 |
| 调度边界 | `balance_max_transfers=32`，`balance_min_gain_us=20`；时间估计的单位均为微秒，换硬件后重新校准。 |
| `num_device_experts` / `num_device_layers` | `[84]` / `2`，决定NPU驻留与显存需求，不是每次路由专家数。 |
| `max_num_tokens` | CPU后端容量48；至少覆盖 `BS × (DSPARK+1)`，增大并发需同时核对图捕获和后端容量。 |
| `KT_MOE_PIN_WEIGHTS` | **1**，开启当前搬运路径所用主存权重固定。 |
| 激活/权重复用 | `KT_MOE_MATCH_NPU_MXFP8=1`、`KT_MOE_MXFP4_TOKEN_REUSE=0`、`KT_GROUP_MIN_LEN=10`；保持本次CPU/NPU计算及成本校准口径。 |
| 热专家与预取 | 热专家预加载开启，使用Ascend源码内匹配的排名JSON；与下一层预取开关不同。预取最多1个，放在本层按需权重就绪后。 |
| 图与服务容量 | `FULL_DECODE_ONLY`，捕获尺寸 `[1,2,3,4,8,16,24,32,48]`；模型长度267000、batched tokens 32000、显存利用率0.90、KV为fp8。 |

以上成本是调度估计，不代表每次真实执行耗时固定。不要删掉CPU结果或预取权重的就绪同步来提高表面吞吐。

## 5. 验证、性能与profile

```bash
unset https_proxy http_proxy HTTPS_PROXY HTTP_PROXY
curl --fail --noproxy '*' http://127.0.0.1:8144/health
curl --fail --noproxy '*' http://127.0.0.1:8144/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"deepseek_v4","prompt":"What is 16 minus 3 minus 4?","max_tokens":20,"temperature":0}'
```

改端口后同步修改curl。profile为delay=2、最大200步；DSpark7短采集用 `max_tokens=20`，让请求自然结束再stop。采集与合成流程见 [profile合成指南](../profile合成指南/README.md)，也可直接复制 [发给agent的合成指令](../profile合成指南/如何让agent合成profile.md)。默认只下载最终trace JSON到本地桌面。

性能测量在关闭采集时单独进行。AISBench perf模式每轮先5条成功预热，再统计20条请求；相同配置重复3次取平均，保持并发、输入集和输出上限一致。
